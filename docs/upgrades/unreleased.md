## What changed

The kit runs on Node 26 with vitest 5, jsdom 30, zod 4, AG-UI 1.0, postgres.js 4 and Anthropic API version 2026-10-21, which a compatible vendor may override; dependencies are current within range; workflows pin Actions by SHA.

- `apps/cli/src/auth.ts`: the callback server's 404 now sends `Connection: close` like its other responses. A kept-alive socket stayed in `fetch`'s pool after `close()`, so the next server on the same port got `ECONNRESET` (deterministic on Node 26's undici 8, a race on Node 24).
- `actions/checkout` v4 → v7.0.1, `actions/setup-node` v4 → v7.1.0, `pnpm/action-setup` v4 → v6.1.0, `actions/upload-artifact` v4 → v7.0.2, `actions/download-artifact` v4 → v8.0.2, each written as `owner/repo@<sha> # vX.Y.Z`. None of the majors changes an input the workflows use: artifacts are downloaded by name, uploads stay zipped, and `setup-node` keeps its explicit `cache: pnpm` (the hardening below then removes it from the two deploy jobs).
- Every `actions/checkout` sets `persist-credentials: false`, so a later step (an artifact upload) cannot publish the `GITHUB_TOKEN` left in `.git/config`. No step pushes or fetches with that token.
- `apps/web/tests/config/ci-workflows.test.ts` asserts the action and its inputs, not the `@v4` tag.
- `apps/web` (`vitest`, `@vitest/coverage-v8`) and `apps/cli` (`vitest`) move from `^3.2.7` to `^5.0.5`. On Node 25+ a stub `localStorage` global shadowed jsdom's and failed every UI test that touched storage; vitest 5's jsdom environment overrides it (3.x and 4.x have no backport). `apps/evals` stays on vitest 4, which `vitest-evals` requires.
- `apps/web/vitest.config.ts`: `poolOptions.forks.{maxForks,minForks}` becomes top-level `maxWorkers` (vitest 4 removed `poolOptions`; the `minForks` pin worked around a vitest 3 bug fixed in 4), and `coverage.all` is gone (removed in vitest 4; `coverage.include` now reports uncovered files on its own).
- Comments and docs that named vitest 3 now name vitest 5 (`docs/EVALS.md`, `docs/CONCEPTS.md` §9, `.claude/rules/testing.md`, `apps/evals/vitest.config.ts`, `apps/web/tests/ui/{setup.ts,jest-dom-vitest.d.ts}`, `scripts/lib/test-plan.mjs`).
- Every dependency moves to the newest release its existing range allows (`pnpm update -r`, 24 h publish delay) — among them `wrangler` 4.156, `hono` 4.13.16, `@biomejs/biome` 2.6.4 and `drizzle-orm` 0.45.4 — and `packageManager` is `pnpm@10.34.9`.
- `@testing-library/jest-dom` moves to `^7.0.1` (6.10.0 was deprecated by its maintainers; 7 makes `@testing-library/dom` a peer, which `auto-install-peers` provides).
- `biome.json` is migrated to the 2.6 schema (`"recommended": true` → `"preset": "recommended"`). Biome 2.6's new `noComponentHookFactories` is off under `apps/*/tests/**` and plugin tests (render wrappers are built inside functions on purpose) and suppressed on `schemaForm`'s `Component`, which `RunAgentModal` creates once in `useState`.
- `apps/web/worker-configuration.d.ts` is regenerated by the newer wrangler.
- **Node 26 is the kit's runtime**: `.nvmrc` is `26` and the root `engines.node` is `>=26`, so CI, `nvm install`/`fnm use` and the bootstrap's toolchain check all require it. The deployed Worker is unaffected (workerd ships its own runtime). `@types/node` moves to `^26.6.6` in `apps/web`, `apps/cli` and `apps/evals`.
- `apps/web`'s `jsdom` moves from `^26.1.0` to `^30.1.3` (its floor on the 24 line is 24.15; none of its four majors needed a test change).
- Docs and skills that named Node 24 now name Node 26 (`CLAUDE.md`, `README.md`, both places in `SETUP.md`, `CONTRIBUTING.md`, the `rf-setup` and `rf-preflight` skills), and `apps/web/scripts/provision.ts` refuses Node below 26 instead of 24.
- Every job sets `timeout-minutes` (about 3–5× its slowest observed run: `ci.yml`'s Gate 15; `deploy.yml` 5 for `guard`/`gated`, 20 for `staging`/`production`, 10 for `release-bundle`), so a hung job stops in minutes rather than after GitHub's 6-hour default.
- `evals.yml` (and the kit's own `kit.yml` and `notify-plugins.yml`) set `permissions: contents: read`; none of them writes with `GITHUB_TOKEN`.
- `deploy.yml`'s `staging` and `production` jobs drop `cache: pnpm`: they run on tags and releases and ship what they build, so a poisoned cache entry would reach a deployed bundle. CI keeps its cache.
- `deploy.yml`'s production "Resolve release version" step reads `github.event.release.tag_name` through `env:` instead of splicing it into the script.
- `ci.yml`'s gitleaks step runs under `shell: bash` (pipefail), downloads with `curl -f` and checks the tarball's SHA-256 before extracting it.
- `evals.yml` quotes the suite filter (`${SUITE:+"$SUITE"}`).
- `zod` moves from `^3.25.76` to `^4.6.7` in `packages/shared`, `apps/web`, `apps/cli` and `apps/evals`. It travels with AG-UI 1.0 because each needs the other: AG-UI 1.0's validators are zod 4 schemas, and `kitAguiEventSchema` is a `z.discriminatedUnion` over them.
- `@ag-ui/core`, `@ag-ui/encoder` and `@ag-ui/proto` move from `0.0.59` to `1.0.3` (exact pins). The validators now come from `@ag-ui/core/schemas` (the main entry is types only), and zod is a peer, so AG-UI validates with the host's zod. `TOOL_CALL_RESULT.content` is typed `string | ContentPart[]`; the kit still emits strings.
- The protobuf transport now carries `TOOL_CALL_RESULT` (`@ag-ui/proto@1.0.3` has the message), so `PROTO_UNSUPPORTED_EVENTS` is empty and `tests/config/agui-contract.test.ts` round-trips the whole event.
- `zod-to-json-schema` is removed; `toolInputSchema()` (`services/ai/agent-loop.ts`) uses zod 4's `z.toJSONSchema(schema, { target: 'draft-7', io: 'input', unrepresentable: 'any' })`.
- zod 4 applies a field's `.default()` even under `.partial()`, so `example-feature`'s `updateExampleNoteRequestSchema` (a `.partial()` of the create schema) turned `PATCH { title }` into `{ title, body: '' }` and would have wiped the body. It is now built from the create schema's fields with the default unwrapped, and a test pins that an omitted field stays out. No kit schema had the same shape.
- Plugin API (`docs/plugin-api.md`): `JobVariant` is `ZodObject<{ type: ZodTypeAny } & ZodRawShape>` (zod 4 has no `ZodDiscriminatedUnionOption`) and `JobTypeOf` reads the variant's `shape.type`; exported schema types now print with zod 4's names. The analytics plugin 3.4.2 installs and passes the whole suite unchanged.
- Type-level zod 4 changes the kit absorbed: `ZodTypeDef` is gone (`z.ZodType<Output, Input>`), `z.record()` needs a key schema, `invalid_type_error` is `error`, and `ZodObject` takes `<Shape, Config>`.
- `postgres` (postgres.js, the `postgres` driver behind `openDatabase`) moves from `^3.4.9` to `^4.0.0` in `apps/web`, and `apps/evals` now declares it too, so pnpm resolves one `drizzle-orm` (its peer) for both packages instead of two copies whose types do not mix. v4 rewrites the pool and protocol below an unchanged API; on Workers it uses `cloudflare:sockets` (the API bundle grows ~23 KiB gzip). Its one data-facing change — the server now types every parameter, so a `Date` meets a `timestamp`/`date` column as UTC — does not reach the kit: all 42 timestamp columns are `withTimezone: true` and no query passes an untyped `Date`.
- `@anthropic-ai/sdk` moves from `^0.122.0` to `^1.3.0`, which sends API version `2026-10-21` (was `2023-06-01`); migration guide: https://platform.claude.com/docs/en/api/migration-2026-10-21. The SDK is now Apache-2.0 (was MIT).
- The Claude API rejects `temperature`, `top_p` and `top_k` on every model from `2026-10-21`, so the `anthropic` adapter (`services/ai/client.ts`) never sends `temperature`; `ChatParams.temperature` stays for `anthropic_compatible`, `openai`, `openai_compatible` and Workers AI, which still take it. The one non-default caller, the evals judge (`temperature: 0`), now samples at the default on a pre-4.7 Claude judge model; on Claude 4.7+ nothing changes.
- SDK 1.x sends the key as `Authorization: Bearer` (was `X-Api-Key`) for both `anthropic` and `anthropic_compatible`, so the two share one client constructor. A tenant whose `anthropic` provider has a `baseUrl` pointing at a proxy that reads `X-Api-Key` must change the proxy to read `Authorization`.
- `Anthropic.MessageParam` is a union of per-role types in 1.x; `withRollingCacheBreakpoints` (`services/ai/agent-loop.ts`) leaves a `system` message's content alone.
- `anthropic_compatible` vendors also receive `anthropic-version: 2026-10-21` now; the kit's tests stub the vendor, so check yours answers on the new version, and set that config's `apiVersion` to `2023-06-01` if it does not.
- An `anthropic_compatible` AI config takes an optional `apiVersion` (`2023-06-01`, the only value allowed; unset = the SDK's `2026-10-21`), sent as `anthropic-version` in place of the SDK's: a nullable `api_version` column on `ai_configs`, the `apiVersion` field on the config contracts (an empty string or an omitted field clears it), an **API version** select in Settings → AI, and the connection test. Any other provider answers 400 `api_version_unsupported`.
