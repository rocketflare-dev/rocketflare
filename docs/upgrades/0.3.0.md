## What changed

Feature flags have a source (D30): `FEATURES_ENABLED` in `[vars]` decides whether a surface ships in
a deployment at all, and a global admin drives the per-organisation rollout from
`/admin/feature-flags` with no redeploy.

- **The environment layer** — `FEATURES_ENABLED`, comma-separated, fail-closed (blank means none),
  consulted only for a flag whose registry entry sets `environmentGated`. This is what lets
  half-built code be released to production dark.
- **The rollout layer** — `feature_flags` (platform state: `off | on | rollout`, a percentage and
  the unit it counts) and `tenant_feature_overrides` (force on or off for one organisation).
- **Flag keys are code** — `FEATURES` in `packages/shared/src/permissions.ts` plus metadata in
  `packages/shared/src/features.ts`. Adding one needs no migration, and `requireFeature('typo')` is
  a type error rather than a route that 404s for ever.
- **Every gate reads the features ARRAY, never the CASL ability** — `globalAdmin` is `manage all`
  and `support` is granted `access all`, and those wildcards cover `access` on every `Feature:`
  subject (`docs/CONCEPTS.md` §15 records the incident). `applyFeatureFlags` still populates
  `Feature:<name>` for an app that wants permission-style entitlements, but nothing that hides a
  dark surface may use it.
- **A feature ships dark on every door**, and three have no nav entry: the API mounts (an optional
  third element in the mount table, 404 `feature_disabled` rather than 403, because a 403 confirms
  the feature exists); the cube registry (`cubesFor(features)`, filtered per request in
  `routes/cube-api.ts`, while `allCubes` stays whole so `cube-isolation.test.ts` still proves every
  cube's tenant scoping); the dashboard templates
  (`DashboardTemplate.feature` + `listTemplates(features)` — `ensureDefaultDashboards` runs lazily
  on every `GET /api/analytics/pages`, so an ungated template CREATES rows in every organisation on
  the first load after a deploy); and the nav, routes and settings tabs, where `NavGuard` gains a
  `{ feature }` form and a list meaning AND.
- One inert demo flag ships — `example-feature`, a nav item and a page. Delete it.
- Also: a `FeatureFlag` platform subject (reachable only through `manage all`), a `features.changed`
  realtime event, `GET /api/features` and `rocketflare features list` for the effective list, and
  `createTenantForUser({ features })` so a new organisation is seeded with the templates its
  environment actually has.

## How to apply

1. Take `packages/shared/src/features.ts` whole. Add `FEATURES` / `FeatureName` and the
   `FeatureFlag` entry in `CORE_SUBJECTS` to `src/permissions.ts`, `featureDisabled` to
   `ERROR_CODES`, and `features.changed` to both `realtimeEventTypeSchema` and
   `REALTIME_INVALIDATIONS` (roots `[['auth'], ['features']]` — flags ride the session, so the
   session is what has to be re-fetched). Replace the `example-feature` registry entry with your own
   keys; `FEATURES` is a `z.enum`, so it may never be empty.
2. Port `src/db/schema/feature-flags.ts` and run `pnpm db:generate` — never copy the kit's
   migration. Two things not to "fix": `key` is the primary key with no surrogate `id`, and
   `tenant_feature_overrides` has NO composite FK to `tenant_users`, because the person setting an
   override is a global admin who is almost never a member of that organisation and the FK would
   reject every write.
3. Add `feature_flags` to `RLS_EXCLUDED_TABLES` — it is platform-level with no `tenant_id`, and it
   is NOT revoked, so that list is no longer exactly the revoked set and its comment changes.
4. Add `FEATURES_ENABLED = ""` to BOTH wrangler tomls (the parity test compares keys) **and to
   `.dev.vars.example`**. `wrangler dev` reads `[vars]` from `wrangler.toml`, which holds the
   production value — without the local override, a key shipped dark in production is dark on every
   developer's machine.
5. Add the flags `LEFT JOIN LATERAL` to `resolveSession` beside the groups one (zero extra round
   trips), plus `parseFlagRows` — the driver may hand jsonb back as text. Then replace
   `features: []` at BOTH sites in `middleware/auth.ts`; the Bearer path reads its rows alongside
   `listUserGroups` under one `Promise.all`. `resolveFeatures` returns `[]` without a tenant.
6. If the app already had a `[vars]`-only flag (`X_ENABLED` style), keep it working by unioning it
   into `resolveFeatures` — that function is the single seam, and every consumer downstream reads
   the array it returns, so nothing else changes.
7. Pass `features` to `createTenantForUser` at all four call sites: `routes/tenants.ts`,
   `services/admin.ts` (approval) and BOTH branches of `onNoTenant` in `services/auth.ts`, including
   the single-mode bootstrap. Omitting it defaults to `[]` and the page arrives on the first
   `GET /pages` instead — late, never wrong.
8. In single-tenant mode, leave `/admin/feature-flags` outside `requireMultiTenant` (flags are not a
   multi-tenancy concept, and single mode always has a global admin), keep the override sub-routes
   behind it, and keep `PATCH` refusing `state: 'rollout'` with `rolloutUnit: 'tenant'` — a
   percentage over one organisation is all-or-nothing decided by an opaque hash. Counting people is
   the useful unit there.
9. Do not change `featureBucket`. It is a wire format: the hash, the separator and the modulus
   together decide who is inside every live rollout, and touching any of them reshuffles them all.
   `tests/config/features.test.ts` pins golden vectors for that reason.

## Conflicts to expect

- `middleware/auth.ts`, `auth/sessions.ts`, `api/index.ts`, `SideNav.tsx` → all four are edited by
  this release → if you have touched them (most apps have), expect rejects and apply by hand.
- `db/schema/rls.ts` → `RLS_EXCLUDED_TABLES` changes shape from `[...RLS_REVOKED_TABLES]` to a list
  with an extra entry, and its doc comment with it → take the kit's shape.
- `useNavGuard.ts` → the `NavGuard` union gains two members and the hook gains a `session` read →
  switch any re-implemented guard logic to the hook; a re-implementation is what hid the
  ability-wildcard bug in the app this was learned from.
- `listTemplates()`, `ensureDefaultDashboards()`, `recreateTemplates()` → each gains a trailing
  `features` parameter defaulting to `[]` → existing calls compile and templates with no `feature`
  are unaffected; pass it where a template is gated.
- `tests/config/permissions.test.ts` → the "covers every core subject" assertion → add a
  `FeatureFlag` row with all roles `none`.

## Verify

1. `pnpm lint && pnpm typecheck && pnpm test && pnpm build` is green.
2. `pnpm web test:config -- features` passes — the frozen hash, monotonicity and precedence, with no
   database.
3. `pnpm web test:api -- feature-flags` passes — every assertion runs as a global admin as well as
   as an owner.
4. With `pnpm dev` running and signed in as a global admin, switch the demo flag on at
   `/admin/feature-flags` and watch a second browser signed in as a member pick it up without a
   reload — that is the `features.changed` nudge.
5. Force the same flag off for that one organisation and confirm it disappears there while the
   platform state still says on.
6. Confirm the nav item is hidden from the GLOBAL ADMIN too while the flag is off — that is the
   difference between a flag and a permission, and it is the thing to check.
