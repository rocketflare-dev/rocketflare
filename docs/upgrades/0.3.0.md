## What changed

**Feature flags have a source (D30).** `AbilityContext.features` shipped as a live seam with nothing
feeding it — `middleware/auth.ts` passed `[]` and `docs/CONCEPTS.md` §1 recorded the source as
undecided. It is now two layers, composed in one pure function:

1. **Environment** — `FEATURES_ENABLED` in `[vars]`, a comma-separated list of the keys a deployment
   ships at all. Fail-closed (blank means none), consulted only for a flag whose registry entry sets
   `environmentGated`. This is what lets half-built code be released to production dark.
2. **Rollout** — `feature_flags` (platform state: `off | on | rollout`, a percentage and the unit it
   counts) and `tenant_feature_overrides` (force on or off for one organisation), both driven by a
   global admin at `/admin/feature-flags` with no redeploy.

Flag KEYS are code: `FEATURES` in `packages/shared/src/permissions.ts` plus metadata in
`packages/shared/src/features.ts`, following the `PROMPT_REGISTRY` and `AGENT_KEYS` precedents.
Adding a flag needs no migration; `requireFeature('typo')` is a type error rather than a route that
404s for ever. One inert demo flag ships (`example-feature`, a nav item and a page) — delete it.

**Every gate reads the features ARRAY, never the CASL ability.** This is the load-bearing rule and
it is not theoretical: an app built on this kit shipped the gate reading the ability and had five
routes open in production to platform staff, because `globalAdmin` is `manage all` and `support` is
granted `access all`, and in CASL those wildcards cover `access` on every `Feature:` subject — while
its cube and dashboard gates read the array and stayed dark. Two sources of truth disagreeing.
`applyFeatureFlags` still populates `Feature:<name>` for an app that wants permission-style
entitlements, but nothing that hides a dark surface may use it.

A feature ships dark on **every door**, and three of them have no nav entry:

- the API mounts — an optional third element in the mount table of `api/index.ts`, so a gated
  surface 404s `feature_disabled` as a whole rather than route by route (404, not 403: a 403
  confirms the feature exists);
- the cube registry — `cubesFor(features)`, filtered per request in `routes/cube-api.ts` while
  `allCubes` stays whole, so `cube-isolation.test.ts` still proves every cube's tenant scoping;
- the dashboard templates — `DashboardTemplate.feature` + `listTemplates(features)`. The sharpest
  one: `ensureDefaultDashboards` runs lazily on every `GET /api/analytics/pages`, so an ungated
  template seeds itself into every organisation on the first load after a deploy. That gate creates
  rows, it does not merely reveal them;
- the nav, routes and settings tabs — `NavGuard` gains a `{ feature }` form and a list meaning AND.

Also: a new `FeatureFlag` platform subject (reachable only through `manage all`), a
`features.changed` realtime event, `GET /api/features` and `rocketflare features list` for the
effective list, and `createTenantForUser({ features })` so a new organisation is seeded with the
templates its environment actually has.

## How to apply

- **`packages/shared`**: take `src/features.ts` whole; add `FEATURES` / `FeatureName` and the
  `FeatureFlag` entry in `CORE_SUBJECTS` to `src/permissions.ts`; add `featureDisabled` to
  `ERROR_CODES`; add `features.changed` to `realtimeEventTypeSchema` and to
  `REALTIME_INVALIDATIONS` (roots `[['auth'], ['features']]` — flags ride the session, so the
  session is what has to be re-fetched). Replace the `example-feature` registry entry with your own
  keys; `FEATURES` is a `z.enum`, so it may never be empty.
- **Schema**: port `src/db/schema/feature-flags.ts` and run `pnpm db:generate` — never copy the
  kit's migration. Two things not to "fix": `key` is the primary key with no surrogate `id`, and
  `tenant_feature_overrides` has NO composite FK to `tenant_users` (the person setting an override
  is a global admin who is almost never a member of that organisation, so the FK would reject every
  write). Add `feature_flags` to `RLS_EXCLUDED_TABLES` — it is platform-level with no `tenant_id`,
  and it is NOT revoked, so that list is no longer exactly the revoked set and its comment changes.
- **`[vars]`**: add `FEATURES_ENABLED = ""` to BOTH wrangler tomls (the parity test compares keys)
  **and to `.dev.vars.example`**. `wrangler dev` reads `[vars]` from `wrangler.toml`, which holds the
  production value — without the local override a key you ship dark in production is dark on every
  developer's machine.
- **Auth path**: add the flags `LEFT JOIN LATERAL` to `resolveSession` beside the groups one (zero
  extra round trips), plus `parseFlagRows` — the driver may hand jsonb back as text. Then replace
  `features: []` at BOTH sites in `middleware/auth.ts`; the Bearer path reads its rows alongside
  `listUserGroups` under one `Promise.all`. `resolveFeatures` returns `[]` without a tenant.
- **If you already had a `[vars]`-only flag** (`X_ENABLED` style): keep it working by unioning it
  into `resolveFeatures` — that function is the single seam, and every consumer downstream reads the
  array it returns, so nothing else changes.
- **Threading `features`**: `createTenantForUser` takes it, and all four call sites pass it —
  `routes/tenants.ts` (the actor's own), `services/admin.ts` (approval) and BOTH branches of
  `onNoTenant` in `services/auth.ts`, including the single-mode bootstrap. Omitting it defaults to
  `[]`, and the page arrives on the first `GET /pages` instead — late, never wrong.
- **Single-tenant mode**: `/admin/feature-flags` is NOT behind `requireMultiTenant` (flags are not a
  multi-tenancy concept, and single mode always has a global admin — `onNoTenant` returns null
  unless `isGlobalAdmin`). The override sub-routes ARE, and `PATCH` refuses
  `state: 'rollout'` with `rolloutUnit: 'tenant'` there, because a percentage over one organisation
  is all-or-nothing decided by an opaque hash. Counting people is the useful unit in single mode.
- **Do not change `featureBucket`.** It is a wire format: the hash, the separator and the modulus
  together decide who is inside every live rollout, and touching any of them reshuffles them all.
  `tests/config/features.test.ts` pins golden vectors for that reason.

## Conflicts to expect

- `middleware/auth.ts`, `auth/sessions.ts`, `api/index.ts` and `SideNav.tsx` are all edited — if you
  have touched them (most apps have), expect rejects there rather than clean application.
- `db/schema/rls.ts`: `RLS_EXCLUDED_TABLES` changes shape from `[...RLS_REVOKED_TABLES]` to a list
  with an extra entry, and its doc comment changes with it.
- `useNavGuard.ts`: the `NavGuard` union gains two members and the hook gains a `session` read. An
  app that re-implemented guard logic anywhere must switch to the hook — a re-implementation is what
  hid the ability-wildcard bug in the app this was learned from.
- `listTemplates()` and `ensureDefaultDashboards()` / `recreateTemplates()` gain a trailing
  `features` parameter. Both default to `[]`, so existing calls compile; templates with no `feature`
  are unaffected.
- `tests/config/permissions.test.ts` needs a `FeatureFlag` row (all roles `none`) or its
  "covers every core subject" assertion fails.

## Verify

```bash
pnpm lint && pnpm typecheck && pnpm test && pnpm build
pnpm web test:config -- features     # the frozen hash, monotonicity, precedence — no database
pnpm web test:api -- feature-flags   # every assertion runs as a global admin as well as an owner
```

Then, signed in as a global admin with `pnpm dev` running: open `/admin/feature-flags`, switch the
demo flag on and watch a second browser signed in as a member pick it up without a reload (the
`features.changed` nudge); force it off for that one organisation and watch it disappear while the
platform state still says on; and confirm the nav item is hidden from the GLOBAL ADMIN too while the
flag is off — that is the difference between a flag and a permission, and it is the thing to check.
