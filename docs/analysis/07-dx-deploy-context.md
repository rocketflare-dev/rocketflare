# 07 — Developer experience, tooling, deployment, and the agent-context system

Analysis of `~/work/mirevue` (structural reference, Node/Docker) and
`~/work/guidemode/apps/server` (Cloudflare substrate reference, pnpm monorepo) for the
Cloudflare-Workers-first, single-package starter kit. Conclusions and file pointers; no
secret values are reproduced anywhere in this document (see §9 for hygiene findings).

**Headline decisions**

| Area | Base | Take from the other | Strip |
|---|---|---|---|
| Tooling (biome/tsconfig/scripts) | Mirevue | GM: `wrangler types`, worker-configuration.d.ts, `.wrangler`/typegen ignores | Mirevue: Docker/tsx runtime, ORT/voice/eval/rewired scripts; GM: monorepo filters, `.npmrc` GH registry |
| Testing | Mirevue (4 projects, shared/isolated split, contract test) | GM: `cloudflare:workers` alias mock, `wrangler-cpu-limits.test.ts` idea → generic toml-parity test | Mirevue: pg-boss teardown, `documents` project; GM: pacing-off, Neon test DB |
| wrangler config | GM `wrangler.toml` + `wrangler.staging.toml` | — | All app bindings (11 workflows, R2/Vectorize/AI/AE, 8 crons), the CPU-limit essay, the DO split |
| CI/CD | GM `deploy-server.yml` (release dance) + Mirevue `ci.yml` (single gate, `workflow_call`) | — | GM: monorepo `--filter` builds, notifications worker step, desktop/packages tag exclusions; Mirevue: Docker/GHCR/SSH deploy, Blacksmith runners, LFS |
| Neon | GM (branches per env, Hyperdrive per env, `-pooler` strip for migrations) | — | Per-PR preview plumbing (`PREVIEW_DATABASE_URL`) |

| Scripts | Mirevue `migrate.ts`, `seed.ts`, `tunnel-dev.mjs` | GM `migrate.ts` Neon branch (direct-host rewrite) | Everything else in both `scripts/` dirs |

## 1. Tooling config

### 1.1 Biome — identical rules, GM has more ignores

`~/work/mirevue/biome.json` and `~/work/guidemode/biome.json` have byte-identical `linter`,
`formatter` and `javascript` blocks (schema 1.9.4; single quotes, `asNeeded` semicolons,
100 cols, `useImportType`/`useExportType` error, `noUnusedVariables` error, a11y rules off,
`noExplicitAny` warn, scripts override to off). The only differences are in `files.ignore`:
GM adds `**/worker-configuration.d.ts`, `**/.wrangler/**`, `**/.astro/**`, `**/src-tauri/**`,
`**/target/**`, `**/gen/**`, `**/generated/**`, `**/reports/**`, `**/.turbo/**`.

**Kit:** Mirevue's file + `**/worker-configuration.d.ts` and `**/.wrangler/**`. Both repos
exclude `tests/**` from lint entirely — keep (it's what lets test files use `any` freely),
but note it means Biome never sees test code. Both are on Biome 1.9.4; 2.x is a config
migration (`biome migrate`) — decide once for the kit (§8e).

### 1.2 tsconfig

| | Mirevue `tsconfig.json` | GM `apps/server/tsconfig.json` |
|---|---|---|
| target/lib | ES2022, DOM, DOM.Iterable | same |
| module/resolution | ESNext / bundler, `noEmit`, `allowImportingTsExtensions`, `isolatedModules` | same + `composite`, `declaration`, `outDir`, `rootDir` (monorepo refs) |
| `types` | `["vite/client", "node"]` | `["vite/client"]` — **no `node`**; Workers globals come from `worker-configuration.d.ts` |
| `paths` | `@/* → src/*`, `@shared/* → src/shared/*` | none (uses `@guidemode/types` workspace pkg) |
| `include` | `src, tests, scripts, evals, *.ts` — tests and scripts ARE typechecked | `src/**/*, worker-configuration.d.ts` — tests/scripts are NOT typechecked |
| references | — | `../../packages/types` |

`worker-configuration.d.ts` (GM, 550 KB, **git-tracked**) is generated by `wrangler types`
(`package.json` `build` = `wrangler types && npm run typecheck && ...`). It emits a global
`interface Env` from every binding and every `[vars]`/`.dev.vars` name (values appear only for
`[vars]`, e.g. `RELEASE_VERSION: "dev"`; `.dev.vars` entries are typed `string`). There is no
`@cloudflare/workers-types` devDependency in GM — only a vestigial root `pnpm.overrides` entry.
GM's `src/types/env.ts` comment confirms: "Types like DurableObjectNamespace, Fetcher,
KVNamespace ... are now available globally from worker-configuration.d.ts".

**Kit:** Mirevue's tsconfig (paths, tests+scripts included, no composite) plus
`worker-configuration.d.ts` in `include`. Keep `"node"` in `types` because `scripts/` and
vitest run under Node; `@types/node` and the wrangler-generated runtime types coexist under
`skipLibCheck` in practice (Mirevue already ships DOM+node together). If collisions appear
(`Request`/`Response` overload noise), split into `tsconfig.json` (worker: `src/api`, `src/db`,
`src/shared`, typegen file, no `node`) + `tsconfig.node.json` (`scripts`, `tests`, `*.config.ts`)
— flagged in §8e rather than done pre-emptively. Add `"types": "wrangler types"` script and run
it in `pretypecheck`/`prebuild`; commit the generated file so `tsc` works in a fresh clone
without wrangler having run (GM's choice; also means `pnpm typecheck` in CI needs no wrangler
auth — `wrangler types` itself needs none either).

Proposed kit block: §8b.

### 1.4 Node / pnpm / npmrc

- GM: `.nvmrc` = `24`; `engines.node >= 24.0.0`, `pnpm >= 9`; `packageManager pnpm@9.15.0`.
  Mirevue: no `.nvmrc`, `engines.node >= 24`, same `packageManager`. **Kit:** add `.nvmrc` (24),
  keep `engines`, keep `packageManager` (consider pnpm 10 — §8e).
- GM `.npmrc` sets a `@guideai-dev` GitHub Package Registry scope (app-specific) plus
  `dedupe-peer-dependents=true`, `strict-peer-dependencies=false`. **Kit:** only the two
  pnpm settings, or omit the file entirely (single package needs neither).
- GM root `pnpm.overrides` is a 20-line CVE-pin list — not for the kit; run `pnpm audit`.

### 1.5 .gitignore / .dockerignore

Mirevue's `.gitignore` is the better model: short, every non-obvious line carries the reason
(e.g. why `.env.test` IS committed, why `evals/runs/` is not). GM's is a 150-line boilerplate
list with the CF-specific essentials buried at the end.

**Kit `.gitignore` essentials:** `node_modules/`, `dist/`, `coverage/`, `*.log`, `.DS_Store`,
`.env`, `.env.local`, `.dev.vars` (+ keep `.dev.vars.example`, `.env.test`, `.env.example`
committed), `.wrangler/`, `.cfld.json`, `*.tsbuildinfo`, `.claude/worktrees/`,
`.claude/settings.local.json`, `bundle-analysis*.html`. Decide on `worker-configuration.d.ts`
(§1.2 says commit). GM currently git-tracks `apps/server/bundle-analysis-ui.html` (407 KB) and
`tsconfig.tsbuildinfo` sits untracked at 1.1 MB — add both patterns.

No `.dockerignore` in the kit (no Dockerfile — §8e for the dual-target question). If a Node
target is ever added, Mirevue's `.dockerignore` (`~/work/mirevue/.dockerignore`) is the model.

### 1.6 concurrently / dotenv-cli

Both use the identical `concurrently --restart-tries 50 --restart-after 2000 --names api,ui
-c blue,green` line. Both use `dotenv -e <file> --` to inject env into Node-side commands.
Differences that matter for the kit:

- Mirevue's server reads `.env` (Node). GM's worker reads `.dev.vars` automatically via
  `wrangler dev`; `dotenv -e .dev.vars` is used only for Node-side tools (drizzle-kit,
  `tsx scripts/*`, vite for `HMR_HOST`). **Kit:** `.dev.vars` is the single local secrets file;
  `dotenv -e .dev.vars --` for every Node-side script; `.env.test` for vitest.
- `dotenv-cli` does not override variables already in the environment — `tunnel-dev.mjs`
  relies on that (§1.7).

### 1.7 cfld (`@cliftonc/cfld`, `.cfld.json`)

What it is: a wrapper around `cloudflared` that gives each developer a **persistent named
tunnel hostname** under a Cloudflare zone, stores the mapping in `.cfld.json`
(`name`, `zone`, `uuid`, `hostname`, `port`, `envKey`), and can run a child command with the
public URL injected under `envKey` (both repos: `PUBLIC_URL`). Both `.cfld.json` files are
git-ignored (`~/work/mirevue/.gitignore`, GM root `.gitignore`) — but Mirevue's copy is still
named `exec-platform` (a previous product name), i.e. it is stale per-developer state, which
is exactly why it is ignored.

Two integration styles:
- **Mirevue** (`scripts/tunnel-dev.mjs`, `vite.config.ts:19-24`): `cfld -- node
  scripts/tunnel-dev.mjs` → script promotes `PUBLIC_URL` to `APP_URL` and spawns `pnpm dev`;
  Vite derives `allowedHosts` and `hmr.host` from `PUBLIC_URL`. Self-contained, no extra vars.
- **GM** (`vite.config.ts:72-82`, `.env` with `HMR_HOST`/`PUBLIC_URL`/`VITE_ORIGIN`):
  `allowedHosts: ['.guidemode.dev']` (whole zone) and a manually maintained `HMR_HOST`.
  Root scripts `tunnel:setup` / `tunnel:start` (`cfld setup` / `cfld`).

**Kit:** include `@cliftonc/cfld` as a devDependency with Mirevue's `dev:tunnel` +
`tunnel-dev.mjs` + Vite derivation. One change is required for Workers: `wrangler dev` does not
read the process environment as Worker vars, so `tunnel-dev.mjs` must pass the URL explicitly —
spawn `pnpm dev:api -- --var APP_URL:${PUBLIC_URL}` (or write it into `.dev.vars` for the
session). Document `pnpm exec cfld setup` as the first-run step (GM's `tunnel:setup`).

## 2. Testing harness

### 2.1 Mirevue (`~/work/mirevue/vitest.config.ts`, 8 KB)

- Four projects: `api` (node, real Postgres, `isolate:false` via CLI flag), `api-isolated`
  (same, default isolation), `documents` (node, no DB), `ui` (jsdom, `@vitejs/plugin-react`,
  `tests/ui/setup.ts`).
- The api split: a file opts into its own module registry with a first-line
  `// @vitest-isolate` marker; `tests/helpers/isolation.ts` is the single rule read by both the
  config (to build the two `include` lists) and `tests/api/isolation-contract.test.ts` (fails CI
  if a file uses `vi.mock`/`vi.stubGlobal`/`vi.spyOn(globalThis…)` without the marker). Measured
  rationale in the config comments (collect 21.7s → 3.3s). Because vitest 3 resolves `isolate`
  per run, `pnpm test` is two `vitest run` invocations (`test:shared`, `test:isolated`).
- Pool: `forks`, `maxForks = minForks = min(6, max(3, cpus-2))` (`vitest.config.ts:27`) with the
  reason for pinning `minForks` (tinypool teardown race, vitest#8564).
- `globalSetup` `tests/setup.ts`: memoised on `globalThis` because two projects share it
  (`tests/setup.ts:49-60`); applies DB roles → migrates → grants → truncates → seeds one
  user/tenant/API key exposed via `provide()`/`inject()`. Per-file `setupFiles`
  `tests/api-setup.ts` closes pools/pg-boss/NOTIFY client after each file (connection budget).
- Requests: `apiRequest()` (`tests/helpers/request.ts`) drives the real `app` from
  `src/api/index` through all middleware; per-file random `TEST_CLIENT_IP` for rate-limit
  isolation. Factories in `tests/helpers/auth.ts` use `uniqueId()` for parallel safety.
- Safety: `tests/helpers/db.ts` `safetyCheck()` requires `NODE_ENV=test` and `localhost` in
  both `DATABASE_URL` and `APP_DATABASE_URL`.
- Coverage: v8, `src/api/**`, `src/documents/**`, reporters text/html/json-summary/lcov.
- Test Postgres: `docker-compose.test.yml` on 5433 with `-c max_connections=300`; CI mirrors
  this via `ALTER SYSTEM` + restart (`.github/workflows/ci.yml`).

### 2.2 GuideMode (`~/work/guidemode/apps/server/vitest.config.ts`, 1.6 KB)

- **Plain Node, no `@cloudflare/vitest-pool-workers`, no miniflare** (grep confirms). Worker
  code is made importable by aliasing `cloudflare:workers` to
  `tests/mocks/cloudflare-workers.ts` (stub `DurableObject`, `WorkflowEntrypoint`) —
  `vitest.config.ts:36`. Bindings are passed as a plain object: `callApi()`
  (`tests/helpers/api.ts`) builds a `Request` and calls the Hono app with
  `{ DATABASE_URL: process.env.DATABASE_URL, ...options.env }`; `databaseMiddleware`
  (`src/api/middleware/database.ts:23`) falls back from `c.env.HYPERDRIVE` to `DATABASE_URL`.
  So the DB path under test is postgres-js against local Postgres, not Hyperdrive.
- Single project, `maxForks: 3`, `globalSetup` `tests/setup.ts` (same shape as Mirevue's —
  clearly the ancestor), `setupFiles: tests/pacing-off.ts` (app-specific).
- One config-level test worth generalising: `tests/wrangler-cpu-limits.test.ts` reads both
  wrangler tomls with a regex and asserts `[limits] cpu_ms` is present, equal, and within the
  platform max.
- `tests/README.md` is stale (says tests run against a named Neon test branch; the
  `safetyCheck` in `tests/helpers/db.ts` still whitelists that branch's endpoint name, while
  `docker-compose.test.yml` provides local paradedb on 5437 and `.env.test` points there).

### 2.3 Kit recommendation

Take Mirevue's harness wholesale, minus `documents`, pg-boss and NOTIFY teardown, plus:

1. `resolve.alias['cloudflare:workers'] → tests/mocks/cloudflare-workers.ts` (GM) so
   DO/Workflow classes import under Node. Extend the stub as bindings are added (KV/Queue fakes
   in `tests/mocks/bindings.ts`: an in-memory `KVNamespace`, a `Queue.send` recorder).
2. `tests/helpers/request.ts` `apiRequest()` gains an `env` parameter merged over a
   `testBindings()` default (`DATABASE_URL` from `.env.test`, fake KV, fake queue) — GM's
   `callApi` shape on Mirevue's helper.
3. `tests/config/wrangler-parity.test.ts` (generalised from GM's cpu-limits test, parse with
   `smol-toml` rather than regex): both tomls declare the same set of binding names and class
   names; every account-scoped name in staging (`workflows[].name`, `queues.*.queue`,
   `kv_namespaces[].id`, `hyperdrive[].id`, `r2_buckets[].bucket_name`, `vectorize[].index_name`,
   `analytics_engine_datasets[].dataset`, `durable_objects` `script_name`) differs from
   production; `compatibility_date`/`compatibility_flags`/`[limits]` are equal; no `<PLACEHOLDER>`
   token remains. This is the test that would have caught GM's staging-hijacks-production
   incident (`wrangler.staging.toml:114-122`).
4. Keep `.env.test` committed with dummy values (Mirevue) — GM's is also committed.
5. Do **not** adopt `@cloudflare/vitest-pool-workers` for the default suite: it cannot reach a
   real Postgres through Hyperdrive locally the way `wrangler dev` can, and Mirevue's whole
   value is integration tests against real Postgres. Offer it as an optional `workers` project
   later for DO/Workflow unit tests (§8e).

Projects: `api` (node, real Postgres, shared registry), `api-isolated` (node, real Postgres,
per-file registry), `ui` (jsdom), `config` (node, no DB — the wrangler toml parity test and
any other repo-shape assertions; runs in the `test:isolated` invocation).

Layout:
```
tests/
  setup.ts            # globalSetup (memoised): migrate → truncate → seed → provide()
  api-setup.ts        # per-file afterAll: closeDatabase()
  helpers/{db,auth,request,isolation}.ts
  mocks/{cloudflare-workers,bindings}.ts
  api/*.test.ts       # integration, real Postgres; `// @vitest-isolate` where needed
  api/isolation-contract.test.ts
  config/wrangler-parity.test.ts
  ui/setup.ts, ui/*.test.tsx
```

## 3. Cloudflare config anatomy

### 3.1 `wrangler.toml` vs `wrangler.staging.toml` (GM)

`diff` of `~/work/guidemode/apps/server/wrangler.toml` vs `wrangler.staging.toml` — every
difference, classified:

| Must differ per env | Lines (prod / staging) |
|---|---|
| `name` | `guidemode-server` / `guidemode-server-staging` |
| `routes = [{ pattern, custom_domain = true }]` | absent in prod file (domain managed in dashboard) / `alpha.guidemode.dev` in staging — kit should declare it in **both** |
| `workers_dev`, `preview_urls` | unset / `true` (staging only) |
| `[vars]` URLs: `APP_URL`, `*_REDIRECT_URI` | app vs alpha hosts |
| `queues.producers[].queue`, `queues.consumers[].queue` | `-staging` suffix |
| `workflows[].name` (**account-scoped**) | `-staging` suffix — bindings and `class_name` identical |
| `hyperdrive[].id` | different ids; `localConnectionString` also differs (ports 5436 vs 5432 — a drift, not a design) |
| `kv_namespaces[].id` | different ids |
| `r2_buckets[].bucket_name`, `vectorize[].index_name`, `analytics_engine_datasets[].dataset` | `-staging` / `_staging` suffix |
| `durable_objects.bindings[].script_name` | `guidemode-notifications` / `-staging` |

| Must be identical | Value |
|---|---|
| `main`, `compatibility_date` (`2024-12-02`), `compatibility_flags = ["nodejs_compat"]` | |
| `[placement] mode = "smart"` | |
| `[limits] cpu_ms = 300000` | guarded by a test |
| `[observability.logs] enabled=true, head_sampling_rate=1, invocation_logs=false` | |
| `[assets] directory="./dist/ui", binding="ASSETS", not_found_handling="single-page-application"` | SPA served by the Worker; Hono matches API routes first, catch-all does `c.env.ASSETS.fetch()` (`src/api/index.ts:537`) |
| `[[migrations]]` for DO classes, `[triggers] crons` | |
| all `binding` names and `class_name`s | so application code never branches on environment |

Two operational lessons recorded in the GM files that the kit must carry forward as text:
(1) Workflow names are account-scoped; sharing one between two workers makes the last deployer
own it and run instances under its bindings (`wrangler.staging.toml:114-122`). (2) Workflows
bound CPU **per step** at the 30 s default unless `[limits]` is declared; a value present in
only one env fails silently in the other (`wrangler.toml:27-58`, 30 lines of incident
narrative — keep the fact, drop the essay).

The DO split (`wrangler.notifications*.toml`, `src/do-worker.ts`) exists only because a worker
that *implements* a DO loses preview URLs, and GM once had per-PR previews (since removed). The
kit has no per-PR previews (staging is the review env), so it can keep any DO inside the single
worker and skip the second config and the "deploy notifications first" CI step.

### 3.2 Two files vs `[env.staging]`

Wrangler environments do **not** inherit bindings from the top level — every binding block
must be repeated under `[env.staging]` anyway, and `wrangler deploy --env staging` also changes
the worker name to `<name>-staging` automatically. GM chose two standalone files with a
"keep in sync" comment. **Kit:** two files (explicit, greppable, `-c` selectable) **plus** the
parity test from §2.3 so "keep in sync" is enforced rather than requested.

### 3.3 Kit `wrangler.toml` skeleton

```toml
name = "<APP>"                       # staging: "<APP>-staging"
main = "src/api/index.ts"
compatibility_date = "<TODAY>"       # identical in both files
compatibility_flags = ["nodejs_compat"]
routes = [{ pattern = "<APP_HOST>", custom_domain = true }]   # staging: <STAGING_HOST>
workers_dev = false                  # staging: true is acceptable as a fallback host
preview_urls = false

[vars]
NODE_ENV = "production"
RELEASE_VERSION = "dev"              # overwritten by CI: wrangler deploy --var RELEASE_VERSION:<tag>
APP_URL = "https://<APP_HOST>"
LOG_LEVEL = "info"

[placement]
mode = "smart"

[limits]
cpu_ms = 30000                       # raise deliberately, in BOTH files; parity test enforces equality

[observability.logs]
enabled = true
head_sampling_rate = 1
invocation_logs = false

[assets]
directory = "./dist/ui"
binding = "ASSETS"
not_found_handling = "single-page-application"

[[hyperdrive]]
binding = "HYPERDRIVE"
id = "<HYPERDRIVE_ID>"               # wrangler hyperdrive create <APP>-production --connection-string=...
localConnectionString = "postgresql://<APP>_user:<APP>_pass@localhost:5432/<APP>_dev"

[[kv_namespaces]]
binding = "RATE_LIMIT_KV"
id = "<KV_ID>"                       # wrangler kv namespace create <APP>_RATE_LIMIT[_STAGING]

# Optional blocks the kit ships commented-out, with the create command beside each:
# [[queues.producers]] / [[queues.consumers]]   queue = "<APP>-jobs[-staging]"
# [[r2_buckets]]                                bucket_name = "<APP>-uploads[-staging]"
# [[workflows]]                                 name = "<APP>-example-workflow[-staging]"  (ACCOUNT-scoped)
# [[durable_objects.bindings]] + [[migrations]] for a realtime hub (single worker; no preview URLs)
# [triggers] crons = ["0 2 * * *"]
```

Secrets (never in toml): `OAUTH_ENCRYPTION_KEY`, `RESEND_API_KEY`, OAuth client
ids/secrets, `ANTHROPIC_API_KEY`, and `DATABASE_URL` only as a fallback when Hyperdrive is
absent. Set with `wrangler secret put <NAME> -c wrangler.staging.toml` after the worker
exists (first deploy will 500 until they do — GM README documents the bootstrap order).

### 3.4 `.dev.vars` and env-file conventions (names only)

Mirevue committed examples: `.env.example` (28 names: `NODE_ENV, PORT, APP_URL, LOG_LEVEL,
DATABASE_URL, OAUTH_ENCRYPTION_KEY, RESEND_API_KEY, EMAIL_FROM, SLACK_/MICROSOFT_/GOOGLE_
CLIENT_ID|SECRET, ANTHROPIC_API_KEY, EMBEDDINGS_API_KEY, LANGFUSE_*, BROADCASTER_DRIVER,
STORAGE_*`), `.env.test` (17 names incl. `APP_DATABASE_URL`, `TENANT_SCOPE_MODE`),
`.env.production.example`. Validated at boot by `src/config.ts` (zod).

GM has **no** `.dev.vars.example` despite `README.md` telling users to `cp .dev.vars.example
.dev.vars`. Its live `.dev.vars` (12 KB, git-ignored) carries ~60 names, including desktop
signing material (`APPLE_*`, `TAURI_*`) that has nothing to do with the worker. Env typing is
triplicated and all-optional: `worker-configuration.d.ts` `Env`, `src/types/env.ts`
`CloudflareEnv`, `src/api/middleware/env.ts` `Env` (+ `envMiddleware` merging `c.env` with
`process.env`).

**Kit conventions:**
- `.dev.vars.example` committed, one name per line with a placeholder and a comment; `.dev.vars`
  git-ignored. Baseline names: `DATABASE_URL` (local only — production uses `HYPERDRIVE`),
  `APP_URL`, `OAUTH_ENCRYPTION_KEY`, `RESEND_API_KEY`, `EMAIL_FROM`, `GOOGLE_CLIENT_ID`,
  `GOOGLE_CLIENT_SECRET`, `MICROSOFT_CLIENT_ID`, `MICROSOFT_CLIENT_SECRET`, `LOG_LEVEL`.
- `.env.test` committed (dummy values; `DATABASE_URL` → `localhost:5433`, `NODE_ENV=test`).
- Non-secret per-env config lives in `[vars]`; secrets via `wrangler secret put`; the generated

  pattern) parses `c.env` once per isolate and fails loudly — replaces GM's three optional

## 5. Neon specifics

- **Separation model:** one Neon project, **branches** per environment. Evidence: root
  `README.md:170-172` ("Staging Neon branch", "Production Neon branch", per-PR "isolated Neon
  branch off staging"); `.dev.vars` comments list distinct `ep-*` endpoints for dev/production/
  test under the same project role (a branch-per-env signature); `wrangler.staging.toml:181-183`
  ("Hyperdrive ... with the STAGING Neon branch"). Same role/password across branches is the
  consequence — a compromise of one env's string is a compromise of all (§9).
- **Hyperdrive:** one Hyperdrive config per env, created with `wrangler hyperdrive create
  <name> --connection-string="<that branch's url>"`, id pasted into the matching toml. At
  runtime `createDatabaseWithHyperdrive()` (`src/db/client.ts:95-121`) uses
  `hyperdrive.connectionString` with postgres-js; in `wrangler dev` the same binding yields
  `localConnectionString`, so application code has one path. Fallback to `DATABASE_URL`
  auto-selects the `@neondatabase/serverless` HTTP driver when the host is Neon (`isNeonUrl`).
- **Migrations in CI:** `scripts/migrate.ts` (GM) receives the env's `DATABASE_URL` secret and,
  for Neon hosts, **rewrites `-pooler` out of the hostname** so DDL runs on a direct connection
  (`scripts/migrate.ts:34-58`; the comment records a production deploy blocked by a
  `default_transaction_read_only` GUC left on a pooled backend). Uses the neon-http migrator for
  Neon and postgres-js locally. Keep this file nearly verbatim.
- **Tests:** never Neon in the kit — local Docker Postgres only (GM's `safetyCheck` allowance
  for a Neon test branch should not be carried over).
- **Kit decision:** default to branches (`production` = Neon `main`, `staging`) with the
  trade-off written in `docs/DEPLOY.md`: branches are cheap and share compute quota/role;
  separate projects give separate credentials and quotas. Recommend a dedicated Neon role per
  branch even within one project. Whether Hyperdrive should be pointed at the pooled or direct
  Neon host is an open question (§8e) — Hyperdrive pools itself.

| `src/**/CLAUDE.md` | routes, middleware, db/schema, shared, permissions, ui — one paragraph of purpose + pointer to rule + file→contract table | 1–3 KB each |
| `.dev.vars.example`, `wrangler*.toml` | Every name/binding carries a one-line comment with the create command or purpose — these files are documentation too | — |

**Onboarding path** (what an agent reads, in order, after copying the kit):
1. `CLAUDE.md` (auto-loaded) — learns the shape and the three pointers.
2. `docs/ADAPTING.md` — because the identity block says "if this is a fresh copy, start here":
   renames, deletions, and the instruction to run SETUP Part 1 next.
3. `SETUP.md` Part 1 — *executed*, not read: DB up, migrate, seed, dev, tests green.
4. `docs/CONCEPTS.md` — before building the first feature, to know what already exists.
5. `.claude/rules/<layer>.md` — loaded automatically by glob when touching that layer.
6. `src/<dir>/CLAUDE.md` — when entering a directory.
7. `SETUP.md` Part 3 + `docs/DEPLOY.md` — when the user asks to ship.

### (d) Resource-provisioning checklist for a new app on Cloudflare (staging and production)

1. Cloudflare: account on Workers Paid if `[limits]`, Hyperdrive, or Workflows are used; a zone
   for `<APP_HOST>` / `<STAGING_HOST>`. `wrangler login` locally.
2. CI API token (account scope): Workers Scripts, KV, Queues, Workflows, Durable Objects,
   Hyperdrive, R2 (edit); Workers AI + Analytics (read) if used; Zone DNS (edit) on the zone.
3. Neon: create project; branches `production` (main) and `staging`; one role per branch;
   record **direct** and **pooled** connection strings for each.
4. Hyperdrive ×2: `wrangler hyperdrive create <APP>-production --connection-string="<neon url>"`
   → `id` into `wrangler.toml`; repeat with `-staging` → `wrangler.staging.toml`.
5. KV ×2: `wrangler kv namespace create <APP>_RATE_LIMIT` / `..._STAGING` → ids.
6. Queues (if enabled) ×2: `wrangler queues create <APP>-jobs` / `<APP>-jobs-staging`.
7. R2 (if enabled) ×2: `wrangler r2 bucket create <APP>-uploads` / `-staging`.
8. Workflows: no create step — but every `name` in staging **must** carry `-staging`
   (account-scoped). Durable Objects: declared in toml with a `[[migrations]]` tag.
9. Local: `cp .dev.vars.example .dev.vars`, generate `OAUTH_ENCRYPTION_KEY`
   (`openssl rand -hex 32`), `pnpm dev:db:up && pnpm db:migrate && pnpm seed`.
10. GitHub: Environments `staging` and `production`; secrets `DATABASE_URL` (that branch,
    pooled or direct — migrations strip `-pooler` themselves), `CLOUDFLARE_API_TOKEN`,
    `CLOUDFLARE_ACCOUNT_ID`.
11. First deploy per env via `workflow_dispatch` (worker must exist before secrets can be set).
12. Secrets per worker: `wrangler secret put <NAME> [-c wrangler.staging.toml]` for every
    non-`[vars]` name in `.dev.vars.example` (or `wrangler secret bulk`).
13. OAuth apps: redirect URIs for `https://<STAGING_HOST>/auth/<provider>/callback`,
    `https://<APP_HOST>/...`, `http://localhost:3000/...`, and the cfld tunnel host.
14. Custom domains: `routes = [{ pattern, custom_domain = true }]` in each toml; wrangler
    creates the DNS records on deploy.
15. Release: bump `package.json` version → commit → `git tag X.Y.Z && git push origin X.Y.Z`
    (staging) → verify at `<STAGING_HOST>` (`/api/health`, version in nav) →
    `gh release create X.Y.Z --generate-notes` (production).
16. `pnpm test` runs `tests/config/wrangler-parity.test.ts` — it fails while any `<PLACEHOLDER>`
    remains or any staging name collides with production.

`scripts/cf-provision.sh <staging|production> <APP>` should execute steps 4–7 and print the
ids (optionally `sed` them into the matching toml).

### (e) Open questions and risks

1. **Node types vs Workers runtime types in one tsconfig.** Mirevue typechecks `tests/` and
   `scripts/` (Node); GM avoids `@types/node` and does not typecheck tests at all. The kit
   wants both. Start with one tsconfig + `skipLibCheck`; fall back to a two-config split if
   `Request`/`Response`/`fetch` overload conflicts surface.
2. **Commit `worker-configuration.d.ts` or regenerate?** GM commits it (550 KB). Committing
   keeps `tsc` working without wrangler; regenerating avoids churn. Proposal: commit +
   `pretypecheck` regenerates; CI fails if the diff is dirty.
3. **Two tomls + parity test vs `[env.staging]`.** Proposed: two files (§3.2). Revisit if
   wrangler adds binding inheritance.
4. **RLS through Hyperdrive.** Mirevue's `TENANT_SCOPE_MODE` pins a connection and sets a
   session GUC (`app.tenant_id`); SETUP.md warns "session-mode pooling only". Hyperdrive and
   Neon's pooler are transaction-pooling; the pattern must become `SET LOCAL` inside a
   transaction per request, and `db-roles.ts` + a second Hyperdrive for `APP_DATABASE_URL` are
   the cost. Decision belongs to the DB subsystem; DX impact is whether `db:roles`, the
   `APP_DATABASE_URL` binding and the `RLS-ROLLOUT.md` runbook ship in v1.
5. **Realtime on Workers.** Mirevue's `ws` server does not exist on Workers; GM uses a DO
   (`NotificationsHub`) split into a second worker purely to keep preview URLs. Proposal: one
   worker, DO inside, `preview_urls = false`. If per-PR previews are ever wanted, GM's
   `do-worker.ts` + `wrangler.notifications*.toml` is the recipe.
6. **Queue substrate.** pg-boss (Mirevue) is Node-only; the kit's background work must be CF
   Queues/Workflows (GM). `queue-init.ts` and the pg-boss teardown in tests disappear;
   `tests/mocks/bindings.ts` gains a recording `Queue`. Owned by the background-work subsystem.
7. **Optional `@cloudflare/vitest-pool-workers` project** for DO/Workflow unit tests alongside
   the Node integration suite — not in v1.
8. **Pooled vs direct Neon host behind Hyperdrive.** GM points Hyperdrive at the `-pooler`
   host (staging create command in `apps/server/README.md`); Hyperdrive pools itself.
   Check current Cloudflare/Neon guidance before fixing the DEPLOY.md recommendation.
9. **Neon branches vs projects** (§5) — default branches, document the trade-off.
10. **Version bump discipline.** The tag-must-equal-package.json check (GM) is deliberate
    friction; a `scripts/release.sh` removes the toil without removing the check.
11. **Biome 1.9 → 2.x, pnpm 9 → 10, `compatibility_date`** — all three should be set fresh
    for the kit (GM's `2024-12-02` is stale; Mirevue has no equivalent).
12. **Runners:** Mirevue uses paid Blacksmith runners; kit uses `ubuntu-latest` with the
    `max_connections` step retained (it was a real 1-in-8 flake).
13. **Multi-agent file strategy** (§6.7): symlink `AGENTS.md → CLAUDE.md` — confirm the target
    tools follow symlinks on all platforms (Windows checkouts may materialise a text file
    containing the path).
14. **Dual target (Node/Docker as well as Workers)?** Mirevue's Dockerfile/entrypoint/compose
    are excellent but the kit is CF-first; keeping a `src/server.ts` Node adapter doubles the
    testing surface. Proposal: no, with the Mirevue files named in ADAPTING.md as the recipe.
15. **Docs drift is the real risk.** GM has three documents describing two different deploy
    flows, a `tests/README.md` describing a database the tests no longer use, managed blocks
    pointing at a deleted `openspec/`, and a `gemini.md` naming a billing provider the code
    replaced. Mirevue avoids this by (i) having fewer files, (ii) stating in each file what it
    is *not*, and (iii) the CLAUDE.md instruction to "update the relevant section when you
    change how one of those works". Encode that as a Non-Negotiable and consider a CI check that
    every `src/**/CLAUDE.md` directory still exists and every `docs/*.md` is linked from
    CONCEPTS or CLAUDE.md.
