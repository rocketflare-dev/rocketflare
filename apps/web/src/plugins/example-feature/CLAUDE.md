# `example-feature` — the reference plugin (D31, decision 3)

**It exists to be read first and deleted second.** Between its four published entries it exercises
every slot the seam has, on the smallest thing that could need one: a notes list. Nothing in the
kit depends on it. `../CLAUDE.md` is the seam it plugs into.

| Slot | Here |
|---|---|
| `SharedPlugin.features` | `example-feature`, one flag gating the nav item, the page and the mount (the kit itself now ships none) |
| `SharedPlugin.subjects` | `ExampleNote`, granted per role by `ServerPlugin.grants` — admin-level `manage`, member `read` + `create` |
| `SharedPlugin.jobs` | `example-feature.ping`, the smoke job; the shortest handler in the repo is `jobs/ping.ts` |
| schema | `example_notes` — `tenantRef()` + `timestamps()` + `tenantIsolation()`, indexes led by `tenant_id`; migration `0012`, generated by the HOST |
| `ServerPlugin.mounts` | `/api/example-feature` CRUD behind `requireFeature(EXAMPLE_FEATURE_FLAG)` — the gate is on the MOUNT, 404 not 403 |
| `ServerPlugin.publicMounts` | `/api/hooks/example-feature/ping` (D34) — NO session: `POST /api/example-feature/ping-link` mints a `signState` URL carrying the tenant, the public handler `verifyState`s it, re-checks the flag with `ctx.features(tenantId)` (no `requireFeature` can run without auth) and enqueues. The shape of every consent callback and webhook |
| `ServerPlugin.jobHandlers` | `jobs/ping.ts`, checked to cover exactly the variants the shared half declared |
| `ServerPlugin.agentTools` | `list_example_notes` on every agent run's `ctx.tools`, bound to the run's `AccessScope` |
| `ServerPlugin.hooks` | `onTenantCreated` (one welcome note, idempotent by "only when there are none") and `seedDemo` (two notes + the flag at 50 % rollout) |
| `UiPlugin.routes` / `nav` | `/example-feature`, `lazy()`, above the kit's "Organisation" group; route and nav share ONE guard |
| `UiPlugin.queryKeys` | `example-feature:notes` — the same string the server's `entity.changed` nudge carries, declared once in `shared.ts` |
| `CliPlugin.register` | `rocketflare example-feature ping` and `… notes list` |
| its own tests | `tests/{api,ui,config}/`, discovered by the host's projects; the api one pins that tenant B can neither list, read nor delete tenant A's notes |

Two details worth copying rather than re-deriving. **`ctx.interrupt` is not demonstrated here** and
the agent examples in the kit cover it instead; this plugin is about the seam, not the agent
runtime. And **`api/hooks.ts` imports `db/schema/feature-flags` directly**, not `db/schema` — that
barrel re-exports `plugins/schema.ts`, which re-exports this plugin, so the barrel would be a cycle.

## Deleting it

That is the point of it, and it is the check that the seam works. Until `pnpm plugin remove` lands
(Phase B) it is four things:

1. Its three directories — `apps/web/src/plugins/example-feature/`,
   `packages/shared/src/plugins/example-feature/`, `apps/cli/src/plugins/example-feature/`.
2. The five barrel lines that name them (import + list entry in `plugins/{server,ui}.ts`,
   `packages/shared/src/plugins/index.ts`, `apps/cli/src/plugins/index.ts`; the `export *` in
   `plugins/schema.ts`).
3. Its surface in `.rocketflare.json`.
4. `pnpm db:generate` — which emits the `DROP TABLE "example_notes"`; read the SQL, then
   `pnpm db:migrate`.

Then `pnpm lint && pnpm typecheck && pnpm test && pnpm build`. Nothing else in the kit names it.
