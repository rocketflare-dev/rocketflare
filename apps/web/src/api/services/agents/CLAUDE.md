# Agent runtime (D7, D17)

The pg-boss agent runtime ported onto Cloudflare Workflows. One table (`agent_runs`), one event log
(`agent_run_events`), one Workflow class (`AgentRunWorkflow`, `../../workflows/agent-run.ts`), one
registry. "Routes enqueue, never run."

| File | Role |
|---|---|
| `registry.ts` | `AGENTS: Record<AgentKey, AgentDefinition>`; `AgentDefinition = { meta: AgentMeta, run(ctx) }`; `AgentContext` (db, cfg, env, logger, tracer, tenantId, runId, userId, input, `emit`, `checkCancelled`, `chat { client, model, maxOutputTokens }`, `tools` (the built-ins, see below), `checkpoint { load, save }` (the tool loop's resume point), `once(key, fn)` (the durable-effect key), `interrupt(ask)` / `steering()` / `artifact(input)` / `approvals` (issue #17, below), `prompt(vars)`, `step(...)`) |
| `interrupts.ts` | The asks and the answers: `requestInterrupt` (**create-or-read on `(run_id, key)`** — the idempotency, T2), `listInterrupts`, `getInterrupt`/`findInterruptByKey`, `resolveInterrupt` (**one** compare-and-set on `pending`; null → 409), `expireInterrupts`, `approvalsForRun` (settled asks keyed by `toolCallId`, an `expired` one read as a decline), `parseDurationMs`/`interruptExpiryFrom` (`AGENT_INTERRUPT_TIMEOUT` → `expiresAt`; unparseable = no deadline, never a failure), `toAgentRunInterrupt`. `reason` is written ONLY by `aguiReasonFor`; `responseSchema` is DERIVED from `interruptPayloadSchema(spec)`, never hand-written |
| `artifacts.ts` | `upsertArtifact` (**`key` is the upsert key** — a redraft replaces itself, which is what makes it safe on a retry), `listArtifacts`, `toAgentArtifact`. Validated against the shared contract HERE, because the writer is an agent and the size caps are what keep a jsonb column bounded |
| `tools/` | Built-ins on `ctx.tools` (`buildAgentTools(ctx)` in `index.ts` — append app tools there), all scoped by the run's `AccessScope` — its tenant AND the requester's group visibility (D29: `executeRun` builds it at EXECUTE time from `agent_runs.requestedByUserId`, so it is current membership rather than a snapshot from enqueue; a run with no requester reads tenant-wide documents only, and a hidden id is answered exactly like an unknown one, suggestion list included) and all answering JSON. `search-knowledge.ts`: `search_knowledge` = hybrid `searchChunks`, WHOLE passages (≤ `PASSAGE_MAX_CHARS` 4 000) inside a `RESPONSE_MAX_CHARS` 16 000 budget, grouped by document and located in it (`passage` n of `totalPassages`, `charOffset` → the `get_document` offset), default 8 hits; every answer carries `note` (the ranking is nearest-neighbour, NOT a relevance filter — dense search never returns nothing) and, when there is genuinely nothing indexed, `knowledgeBase` + a `hint`; no embeddings provider → `{ error: 'knowledge_search_unavailable', hint }`. `get-document.ts`: `get_document` = one document's text, `{ offset, maxChars }` with `totalChars`/`returnedChars`/`hasMore`/`nextOffset`/`hint`. **The window cap is the CALLER's**, `AgentToolContext.maxDocumentChars` — `GET_DOCUMENT_MAX_CHARS` 50 000 for an agent run, where reading the document IS the job, and `CHAT_GET_DOCUMENT_MAX_CHARS` 6 000 from `chat-turn.ts`, where the result shares one context window with the whole thread. An over-ask is CLAMPED, never rejected: a validation error costs a turn the model cannot diagnose, while a short window plus `nextOffset` is a call it already knows how to make. Dead ends — unknown, other-tenant, unconverted or failed → `{ error, hint }` (+ `knowledgeBase` for an unknown id). `list-documents.ts`: `list_documents` = what exists (indexed only), newest first, paged — `listKnowledgeDocuments` is the shared query the other two borrow for their dead ends. **Rule of thumb: a tool answer must be actionable — never a bare "nothing found", always what to do next.** |
| `examples/summarize-text.ts` | The single-call example: exclusive, precheck, one terminal tool via `callStructuredTool`, `step`/`tool.*`/`text` events, `recordUsage('agent:summarize-text')`, optional `ingestText` when `input.index` |
| `examples/research-topic.ts` | The agentic example: `runToolLoop` over `[...ctx.tools, submit_answer]` capped by `cfg.AGENT_MAX_TURNS`, `ctx.checkCancelled()` in `onStep` (the loop takes no `AbortSignal`), each `onEvent` → an `agent_run_events` row (tool results truncated). A loop ending WITHOUT the terminal call (`no_tool_call`/`max_turns` — Workers AI has no `tool_choice`) is salvaged by ONE `callStructuredTool` over the transcript, not failed; citations are filtered to the document ids the tools actually returned (titles from the search hit), so a hallucinated id is dropped. `recordUsage('agent:research-topic')` once, summed |
| `run-stream.ts` | `GET /runs/:id/agui/stream` (issue #7): `runStreamBody` tails `agent_run_events` on ONE connection (`tailRunEvents`, bounded by `RUN_STREAM_TAIL_LIMIT`, plus the run row for settle/park detection), pushes each row through `createRunProjector` and frames it as AG-UI. `{ now, sleep }` are injected so the tests are not timer-bound. Four rules: the SSE **`id:` goes on the LAST frame of a row's group and nowhere else** (a `text` row is three frames; a mid-group drop must resume at the PREVIOUS row); **no `RUN_ERROR` for the stream's own failure** (decision 6 — closing with no terminal event means *reconnect*); **`reconcileRun` exactly once, in the route, never in the loop** (one Workflow subrequest per call); and **no `: ping` comment frame in binary mode** (not a valid protobuf frame). A parked run needs no branch — `finish` already answers `awaiting_input` with the interrupt outcome, so the connection closes and a seven-day park costs nothing |
| `agui-projection.ts` | `projectRunToAgui(run, events, { interrupts, artifacts })` — a FOLD over `createRunProjector(run) → { head, push, finish }`, the resumable form the stream uses; `finish` takes the run as an ARGUMENT because in a stream the row changes underneath you. Tool calls pair on `data.toolCallId ?? name` (name-only pairing mis-attributes two parallel calls to the same tool) while the EMITTED `toolCallId` stays `event.id`. The run read back as AG-UI. The third argument is the two TABLES, because the log records WHERE an ask or an artifact appeared while the table records what became of it; a row whose entry is absent is skipped, never invented. Every run opens `RUN_STARTED → STATE_SNAPSHOT` with `capabilities.humanInTheLoop`, and a run `awaiting_input` WITH pending asks ends in `RUN_FINISHED { outcome: { type: 'interrupt', … } }` — AG-UI's own delivery, `'interrupt'` not `'interrupted'`. `awaiting_input` with NO pending ask emits no terminal event: that is the window between the resolve write and `resumeRun`, not an impossibility. Read by `GET /api/agents/runs/:id/agui`. PURE: the `agent_run_events` row ids ARE the AG-UI message and tool-call ids, so two projections match byte for byte. `threadId = runId`. A settled `cancelled` run is `RUN_ERROR` with code `agent_run_cancelled` (a finite array cannot say "cancelled" by omitting the terminal event — that is how an ACTIVE run reads); no `kit.usage`, because `ai_usage` rows carry no run id |
| `runs.ts` | `parkRun` (`running → awaiting_input`, **not** a `settle()` — `finishedAt` stays NULL and the checkpoint survives), `resumeRun` (`awaiting_input → running`, the compare-and-set the resolve route does BEFORE it nudges), `nudgeOrRestartInstance` (`sendEvent`, and on `instance.not_found` a NEW instance `<runId>-r1`, `-r2`… — `nextInstanceId`), `expireParkedRun` (the read-path net for a park whose instance is gone), `appendEventAtomic` (`seq` in SQL, one retry on `23505` — for a writer racing a step's emitter), `claimEffect` (replays a DECISION where `runOnce` replays a result), `loadCheckpoint`/`saveCheckpoint` (`agent_runs.checkpoint`; cleared by every settle; an unparseable value reads as "none"), `runOnce` (`agent_run_effects`, unique `(run_id, key)`), `enqueueRun` (validate → insert `queued` → `AGENT_RUN_WORKFLOW.create({ id: runId })` → `instanceId`; partial-unique dedupe → `{ deduplicated: true }`; no binding → 503 `agent_runs_not_configured`), `claimRun` (`UPDATE … WHERE status IN (queued,running) RETURNING`, `attempt+1`), `finishRun`/`failRun`/`cancelRun` (only ever settle an ACTIVE row), `requestCancel(db, tenantId, runId, realtime?, env?)` (queued → cancelled; running → `cancelRequestedAt`; running AND already cancel-requested → FORCE: `instance.terminate()` best-effort, then settle `cancelled`), `reconcileRun` (`instance.status()` on read; `not_found` → failed; no binding → no-op), `appendEvent` + `nudgeRun` |
| `runtime.ts` | The three step bodies as plain functions: `claimStep`, `executeRun`, `finishStep`; `EXECUTE_RETRIES = 2`; error classification (`isRetryableRunError`: only `AiError` unavailable/rate_limit and DB-unavailable rethrow — and only while `attempt <= EXECUTE_RETRIES`; **`false` for both interrupt types**, or a step retry re-asks somebody who already answered). `ExecuteOutcome.status` includes `awaiting_input`. Two catch arms above the classification: `InterruptRequested` → rows, then `parkRun`, then an `interrupt` event and `notifyApprovers` per row behind `claimEffect('notify:<id>')`, then `status: awaiting_input`; `InterruptDeclinedError` → `cancelRun` + `expireInterrupts` + a `status` event carrying `reason: 'rejected'` (`agent_runs.error` stays NULL). `takeSteeringNotes` is the once-only delivery. **`finishStep` has TWO arms**: the failure backstop, whose predicate stays the inline `queued\|running` (T7); and an expiry arm for a row still `awaiting_input` when the WORKFLOW IS ENDING — nothing can wake it now, so it expires the asks and settles `cancelled` with `error` NULL and `reason: 'expired'` on the event row. The one exception is a park the loop ABANDONED (`MAX_INTERRUPT_ROUNDS`), which arrives with `outcome.status === 'failed'` — **the outcome decides that, never the row** |

Rules:

- **Claim is the row, not the queue.** A retried step re-claims and a settled row is never rewritten. **Three status lists, and they diverge on purpose** (issue #17 decision 1): `ACTIVE_RUN_STATUSES` (`queued|running|awaiting_input`) is "still owes an answer" — the exclusive index, `findActiveRun`, `settle()`, `saveCheckpoint`; `CLAIMABLE_RUN_STATUSES` (`queued|running`) is `claimRun` ONLY; and `finishStep`'s backstop keeps its own inline `queued|running`, because widening THAT one turns every legitimately parked run into a `failed` row (its second, expiry arm is a separate branch, not a wider list).
- **Human-in-the-loop: `ctx.interrupt(ask)` parks the run** (issue #17). `key` is the agent's and must be stable across attempts — a resumed `execute` re-enters `run()` from the top, and `UNIQUE (run_id, key)` is what makes the second call find the ANSWER. Everything after the call is **on the far side of a Worker deploy**, so side effects go behind `ctx.once`. **The answer is the transition**: resolving flips `awaiting_input → running` and only then nudges the instance, which is why `claimRun` needs no change. A rejection is `status: 'cancelled'`, never an `approved` boolean; what it MEANS is `rejectionFor(spec)` — `approval` stops the run (`InterruptDeclinedError` → `cancelled`, `error` NULL), everything else goes back to the model as an answer. `executeRun`'s catch arm writes **the rows first and parks second**: a row with no parked run re-asks, a parked run with no row hangs.
- **A gated tool is gated by the LOOP, never by its handler.** `Tool.requiresApproval` / `requiresApprovalWhen` make `runToolLoop` scan the whole turn after the assistant message is pushed and before any handler runs, checkpoint, and raise `InterruptRequested`. On resume, `resumePendingToolCalls` answers the trailing unanswered `tool_use` blocks through **the same** `executeToolUses` — do not fork it, or the gate is bypassed on the resume path only. Pass `approvals: ctx.approvals` and `runApproved: ctx.once` or an approved call re-executes on a step retry.
- **Exclusive = the partial unique index** `agent_runs_active_exclusive_idx`. A non-exclusive agent needs that index relaxed (documented gap; every v1 agent is exclusive).
- **Cancellation is cooperative, then forced**: `requestCancel` sets the flag, the run's `checkCancelled()` polls between turns (and between tool results where the agent does the work in tools); `AgentCancelledError` is a TYPE the runtime maps to `cancelled`. A step in flight finishes. **The second cancel forces it** — terminate the instance, settle the row — because nothing polls in a hung model call or an orphaned instance, and an exclusive agent stuck `running` blocks the tenant. `reconcileRun` reads `terminated` as `cancelled`.
- **DB is the truth, WS is a nudge**: events go to `agent_run_events` first, then `entity.changed { entity: 'agent-run', id }`; viewers re-query `GET /api/agents/runs/:id`.
- **Per-agent model**: `resolveChat(..., { promptKey: meta.promptKey })` consults `agent_models`.
- **Every agent can read the knowledge base**: `ctx.tools` carries `search_knowledge` and `get_document` (everything indexed via `/documents` — pasted or uploaded — or an agent's `ingestText`). Pass `[...ctx.tools, ...ownTools, terminalTool]` to `runToolLoop`; a forced single-tool agent (`callStructuredTool`, like the example) simply does not use it. Never build a retrieval query from a model-supplied tenant id — the tool is bound to the run's tenant.
- **A retry re-enters `run()` from the top, so anything with a side effect goes through `ctx.once(key, fn)`** — an ingest, a ledger write, an outbound call. `agent_run_effects_run_key_idx` is the guarantee; the result is jsonb, so **return ids, not rows**. The contract is at-least-once WITH a recorded result, not exactly-once (an isolate that dies between `fn()` and the insert repeats the work).
- **A resumable loop passes `resume: await ctx.checkpoint.load()` and `onCheckpoint: ctx.checkpoint.save`**, so a retried step continues the conversation instead of replaying and re-billing it, and `maxTurns` becomes a budget for the RUN. State an agent derived from tool results DURING the loop (`research-topic`'s `seen` map) must be rebuilt from the resumed transcript — see `rehydrateSeen`; forget it and citations earned before the retry are silently dropped. A checkpoint that does not parse is `null`: the run starts fresh, never fails.
- **The tool loop runs INSIDE one `execute` step, deliberately.** One `step.do` per model turn was investigated once the durable transcript existed, and rejected: wall-clock per step is unlimited on Workflows (the 10-minute `timeout` is ours to raise), CPU per step excludes I/O and is configurable to 300 s, and per-turn retry is what the checkpoint already gives you. Per-turn steps would need `run()` to move outside `step.do` (steps do not nest), and Workflows replays everything outside a step — so every `emit`, cancel poll, `ctx.once` and tool call would need its own step or the timeline doubles. `docs/CONCEPTS.md` §9 Known gaps carries the full reasoning. Do not re-open it without a profile showing CPU, not I/O, is the limit.
- Adding an agent: key in `@rocketflare/shared/ai/agents` (`AGENT_KEYS` + schemas) → prompt in `services/prompts.ts` → `examples/<key>.ts` → entry in `AGENTS`. No migration.
