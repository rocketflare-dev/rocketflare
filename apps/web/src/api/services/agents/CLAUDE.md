# Agent runtime

The agent runtime on Cloudflare Workflows. One table (`agent_runs`), one event log
(`agent_run_events`), one Workflow class (`AgentRunWorkflow`, `../../workflows/agent-run.ts`), one
registry. "Routes enqueue, never run."

| File | Role |
|---|---|
| `registry.ts` | `AGENTS: Record<AgentKey, AgentDefinition>`; `AgentDefinition = { meta: AgentMeta, run(ctx) }`; `AgentContext` (db, cfg, env, logger, tracer (the step's recorder, `ai_spans` on the step client + OTLP), tenantId, runId, userId, input, `emit`, `checkCancelled`, `chat { client, model, maxOutputTokens }`, `tools` (the built-ins, see below), `checkpoint { load, save }` (the tool loop's resume point), `once(key, fn)` (the durable-effect key), `interrupt(ask)` / `steering()` / `artifact(input)` / `approvals` (below), `decide` (below), `prompt(vars, promptKey?)` — a second key resolves ANOTHER registry prompt, for an agent that runs a second agent's body —, `step(...)`, and `scope(prefix)` / `map(key, items, fn, opts)` (`fanout.ts`) and `recordUsage(call)`) |
| `fanout.ts` | `withFanout(base)` attaches `scope` and `map` to a context — the runtime's and replay's. A scope prefixes every keyed primitive (`once`, `decide` + `sift`/`pick` rebuilt with `decideWithShapes`, `interrupt`, `artifact`, `step`) with `<prefix>/` and has NO checkpoint (one column cannot hold two loops). `map` runs item `i` as `once('key[i]', () => fn(item, scope('key[i]')), { replay: 'inner' })` at most `min(concurrency ?? 4, AGENT_MAP_MAX_CONCURRENCY = 6)` at a time; the first real error stops scheduling and is thrown after the in-flight items settle; `InterruptRequested` does NOT stop scheduling, and every ask is merged into one `InterruptRequested`, in item order — one park |
| `budget.ts` | The run's meter. `createRunMeter` starts from `runSpend` (every attempt's `ai_usage` rows), `check()` before each call (`meta.budget` over `AGENT_RUN_MAX_TOKENS`/`AGENT_RUN_MAX_COST_USD`, then `AGENT_TENANT_DAILY_COST_USD` via `tenantAgentSpendToday`) throws `AgentBudgetExceededError` (never retryable → `failed` + an `error` event with `code: 'agent_budget_exceeded'`), `record()` writes one row with the run id, AWAITED. `meterChatClient` wraps the traced client OUTSIDE the trace (a refused call opens no span); `createDecide` takes the meter as `deps.meter`. `assertTenantDailyBudget` / `TenantBudgetExceededError` (429 `ai_budget_exceeded`) are the enqueue-time half |
| `decisions.ts` | `ctx.decide`: `createDecide(deps)` → callable `(key, { state, questions })` plus `.sift(key, …)` (one request, the same `noul` of every item, kept at the caller's `threshold`) and `.pick(key, …)` (one `choice` over the items + `none`). **Recorded once per `(run_id, key)`** in `agent_run_decisions` — a re-entered `run()` gets the stored answers (`replayed: true`) and the engine is not called; the same key with a different `questions_hash` throws `DecisionKeyConflictError` (the state may change between attempts, the questions may not). The engine is resolved LAZILY on first use (`resolveDecisions`). Each fresh call: `decide <key>` span, row, `ai_usage` (`agent:<key>:decide`), then a thin `decision` event whose answers are in QUESTION order (jsonb reorders keys, so the row cannot be the source). `listDecisions` / `toAgentRunDecision` / `questionsHash` / the pure `siftRequest` / `pickRequest` |
| `interrupts.ts` | The asks and the answers: `requestInterrupt` (**create-or-read on `(run_id, key)`** — the idempotency), `listInterrupts`, `getInterrupt`/`findInterruptByKey`, `resolveInterrupt` (**one** compare-and-set on `pending`; null → 409), `expireInterrupts`, `approvalsForRun` (settled asks keyed by `toolCallId`, an `expired` one read as a decline), `parseDurationMs`/`interruptExpiryFrom` (`AGENT_INTERRUPT_TIMEOUT` → `expiresAt`; unparseable = no deadline, never a failure), `toAgentRunInterrupt`. `reason` is written ONLY by `aguiReasonFor`; `responseSchema` is DERIVED from `interruptPayloadSchema(spec)`, never hand-written |
| `artifacts.ts` | `upsertArtifact` (**`key` is the upsert key** — a redraft replaces itself, which is what makes it safe on a retry), `listArtifacts`, `toAgentArtifact`. Validated against the shared contract HERE, because the writer is an agent and the size caps are what keep a jsonb column bounded |
| `tools/` | Built-ins on `ctx.tools` (`buildAgentTools(ctx)` in `index.ts` — append app tools there), all scoped by the run's `AccessScope` — its tenant AND the requester's group visibility (`executeRun` builds it at EXECUTE time from `agent_runs.requestedByUserId`, so it is current membership rather than a snapshot from enqueue; a run with no requester reads tenant-wide documents only, and a hidden id is answered exactly like an unknown one, suggestion list included) and all answering JSON. `search-knowledge.ts`: `search_knowledge` = hybrid `searchChunks`, WHOLE passages (≤ `PASSAGE_MAX_CHARS` 4 000) inside a `RESPONSE_MAX_CHARS` 16 000 budget, grouped by document and located in it (`passage` n of `totalPassages`, `charOffset` → the `get_document` offset), default 8 hits; every answer carries `note` (the ranking is nearest-neighbour, NOT a relevance filter — dense search never returns nothing) and, when there is genuinely nothing indexed, `knowledgeBase` + a `hint`; no embeddings provider → `{ error: 'knowledge_search_unavailable', hint }`. `get-document.ts`: `get_document` = one document's text, `{ offset, maxChars }` with `totalChars`/`returnedChars`/`hasMore`/`nextOffset`/`hint`. **The window cap is the CALLER's**, `AgentToolContext.maxDocumentChars` — `GET_DOCUMENT_MAX_CHARS` 50 000 for an agent run, where reading the document IS the job, and `CHAT_GET_DOCUMENT_MAX_CHARS` 6 000 from `chat-turn.ts`, where the result shares one context window with the whole thread. An over-ask is CLAMPED, never rejected: a validation error costs a turn the model cannot diagnose, while a short window plus `nextOffset` is a call it already knows how to make. Dead ends — unknown, other-tenant, unconverted or failed → `{ error, hint }` (+ `knowledgeBase` for an unknown id). `list-documents.ts`: `list_documents` = what exists (indexed only), newest first, paged — `listKnowledgeDocuments` is the shared query the other two borrow for their dead ends. **Rule of thumb: a tool answer must be actionable — never a bare "nothing found", always what to do next.** |
| `examples/summarize-text.ts` | The single-call example: exclusive, precheck, one terminal tool via `callStructuredTool`, `step`/`tool.*`/`text` events, optional `ingestText` when `input.index` (usage is the runtime's meter) |
| `examples/research-topic.ts` | The agentic example: `runToolLoop` over `[...ctx.tools, submit_answer]` capped by `cfg.AGENT_MAX_TURNS`, `ctx.checkCancelled()` in `onStep` (the loop takes no `AbortSignal`), each `onEvent` → an `agent_run_events` row (tool results truncated). A loop ending WITHOUT the terminal call (`no_tool_call`/`max_turns` — Workers AI has no `tool_choice`) is salvaged, not failed — by its `meta.policy` (`onExhaustion: 'final-answer'`), which makes the loop force ONE call over the transcript; `onExhausted` only shows it on the timeline; citations are filtered to the document ids the tools actually returned (titles from the search hit), so a hallucinated id is dropped. No ledger code: every turn is one metered row |
| `examples/triage-research.ts` | The decisions example, and the one built-in NON-exclusive agent (any number at once, batchable): one `search_knowledge` call frozen by `ctx.once('triage:search')` (a replayed sift must be about the SAME items), `ctx.decide.sift('relevant', …)`, `ctx.decide('answerable', …)`, then CODE routes — confidence below `ESCALATE_BELOW_CONFIDENCE` → `research-topic`'s own body on its own prompt (`ctx.prompt(vars, 'research-topic')`), P(yes) < 0.5 → "not covered" with no model call, else one forced answer over the kept passages with citations filtered to them. A `table` artifact lists every passage with its probability. The answer call is `ctx.once('triage:answer', fn, { replay: 'rerun' })` — a pure model call a live replay makes again |
| `replay.ts` | Replay: `replayRun(db, cfg, env, run, agent, { mode, logger })` runs an agent's CURRENT code (or a candidate with the same key) over one settled run and returns a `ReplayResult` — `verdict` (`match`/`differs`/`incomplete`), `outputDiff` (`diffJson`, by JSON path, capped), each decision's status (`served` · `drift` reworded · `stale` same questions, different state · `asked` live · `missing` · `unused` recorded, never asked), `misses`, refused `writes`, `reran`. The context answers from the record (`decide` ← `agent_run_decisions`, `once` ← `agent_run_effects`, `interrupt` ← `agent_run_interrupts`, steering ← its events); chat and tool handlers are misses in `strict` and real in `live`. **Read-only twice over**: a READ ONLY transaction per run, and `ctx.db` refuses `insert`/`update`/`delete` before the SQL is sent, so a swallowed write cannot abort the transaction. `decideWithShapes` (`decisions.ts`) is shared so a replay rebuilds the same `sift`/`pick` request and hash. `listReplayableRuns` takes the tenant. Driven only by `scripts/agent-replay.ts` (`pnpm web agent:replay`) |
| `run-stream.ts` | `GET /runs/:id/agui/stream`: `runStreamBody` tails `agent_run_events` on ONE connection (`tailRunEvents`, bounded by `RUN_STREAM_TAIL_LIMIT`, plus the run row for settle/park detection), pushes each row through `createRunProjector` and frames it as AG-UI. `{ now, sleep }` are injected so the tests are not timer-bound. Four rules: the SSE **`id:` goes on the LAST frame of a row's group and nowhere else** (a `text` row is three frames; a mid-group drop must resume at the PREVIOUS row); **no `RUN_ERROR` for the stream's own failure** (closing with no terminal event means *reconnect*); **`reconcileRun` exactly once, in the route, never in the loop** (one Workflow subrequest per call); and **no `: ping` comment frame in binary mode** (not a valid protobuf frame). A parked run needs no branch — `finish` already answers `awaiting_input` with the interrupt outcome, so the connection closes and a seven-day park costs nothing |
| `agui-projection.ts` | `projectRunToAgui(run, events, { interrupts, artifacts })` — a FOLD over `createRunProjector(run) → { head, push, finish }`, the resumable form the stream uses; `finish` takes the run as an ARGUMENT because in a stream the row changes underneath you. Tool calls pair on `data.toolCallId ?? name` (name-only pairing mis-attributes two parallel calls to the same tool) while the EMITTED `toolCallId` stays `event.id`. The run read back as AG-UI. The third argument is the two TABLES, because the log records WHERE an ask or an artifact appeared while the table records what became of it; a row whose entry is absent is skipped, never invented. Every run opens `RUN_STARTED → STATE_SNAPSHOT` with `capabilities.humanInTheLoop`, and a run `awaiting_input` WITH pending asks ends in `RUN_FINISHED { outcome: { type: 'interrupt', … } }` — AG-UI's own delivery, `'interrupt'` not `'interrupted'`. `awaiting_input` with NO pending ask emits no terminal event: that is the window between the resolve write and `resumeRun`, not an impossibility. Read by `GET /api/agents/runs/:id/agui`. PURE: the `agent_run_events` row ids ARE the AG-UI message and tool-call ids, so two projections match byte for byte. `threadId = runId`. A settled `cancelled` run is `RUN_ERROR` with code `agent_run_cancelled` (a finite array cannot say "cancelled" by omitting the terminal event — that is how an ACTIVE run reads); no `kit.usage`, because `ai_usage` rows carry no run id |
| `runs.ts` | `parkRun` (`running → awaiting_input`, **not** a `settle()` — `finishedAt` stays NULL and the checkpoint survives), `resumeRun` (`awaiting_input → running`, the compare-and-set the resolve route does BEFORE it nudges), `nudgeOrRestartInstance` (`sendEvent`, and on `instance.not_found` a NEW instance `<runId>-r1`, `-r2`… — `nextInstanceId`), `expireParkedRun` (the read-path net for a park whose instance is gone), `appendEventAtomic` (`seq` in SQL, one retry on `23505` — for a writer racing a step's emitter), `claimEffect` (replays a DECISION where `runOnce` replays a result), `loadCheckpoint`/`saveCheckpoint` (`agent_runs.checkpoint`; cleared by every settle; an unparseable value reads as "none"), `runOnce` (`agent_run_effects`, unique `(run_id, key)`), `enqueueRun(db, cfg, env, input)` (validate → `input.idempotencyKey`: the run id is `idempotentRunId(tenant, agent, key)` and an existing row under it is the answer, `deduplicated`, settled or not — a `queued` hit with no instance gets one (`ensureInstance`), and a failed `create()` DELETES the idempotent row rather than failing it so the retry starts afresh → the slot (`input.concurrencyKey`, else `''` for an exclusive agent, else NULL): its active run → `{ deduplicated: true }` → `AGENT_MAX_ACTIVE_RUNS_PER_TENANT` (429 `agent_runs_limit`, counting `countActiveRuns`) and the daily spend (429 `ai_budget_exceeded`) → insert `queued` with `concurrency_key` → `AGENT_RUN_WORKFLOW.create({ id: runId })` → `instanceId`; no binding → 503 `agent_runs_not_configured`), `enqueueRunBatch` (non-exclusive only — 400 `agent_exclusive`; per-input validation; capacity for the valid ones; ONE insert under a fresh `batch_id`; ONE `createBatch()`, which is all or nothing, so on a throw each instance is created alone — `already exists` counts as started — and only a real failure settles its row `failed`), `claimRun` (`UPDATE … WHERE status IN (queued,running) RETURNING`, `attempt+1`), `finishRun`/`failRun`/`cancelRun` (only ever settle an ACTIVE row), `requestCancel(db, tenantId, runId, realtime?, env?)` (queued → cancelled; running → `cancelRequestedAt`; running AND already cancel-requested → FORCE: `instance.terminate()` best-effort, then settle `cancelled`), `reconcileRun` (`instance.status()` on read; `not_found` → failed; no binding → no-op; **`{ lastEventAt }` inside `RECONCILE_LIVENESS_MS` (30 s) returns the row without touching the binding** — a run that wrote a durable row two seconds ago is alive by definition, and the run page re-reads on every new `seq`; the argument is opted into per call site, never defaulted), `appendEvent` + `nudgeRun` |
| `runtime.ts` | The three step bodies as plain functions: `claimStep`, `executeRun`, `finishStep`; **tracing**: `executeRun(…, { round })` brackets the attempt as an `execute#N` span in the run's ONE trace (`traceIdForRun`, parent `rootSpanIdForRun` — both derived from the run id because each step is a separate invocation) and flushes in `finally` while the step's client is open; `finishStep(…, outcome, { cfg })` — the `cfg` is passed by the workflow's final `finish` step ONLY, never the `expire#N` call — records the root `invoke_agent <key>` via `recordRunRoot` (never throws); `enqueueRun` writes `agent_runs.trace_id`; `EXECUTE_RETRIES = 2`; error classification (`isRetryableRunError`: only `AiError` unavailable/rate_limit and DB-unavailable rethrow — and only while `attempt <= EXECUTE_RETRIES`; **`false` for both interrupt types**, or a step retry re-asks somebody who already answered). `ExecuteOutcome.status` includes `awaiting_input`. Two catch arms above the classification: `InterruptRequested` → rows, then `parkRun`, then an `interrupt` event and `notifyApprovers` per row behind `claimEffect('notify:<id>')`, then `status: awaiting_input`; `InterruptDeclinedError` → `cancelRun` + `expireInterrupts` + a `status` event carrying `reason: 'rejected'` (`agent_runs.error` stays NULL). `takeSteeringNotes` is the once-only delivery. **`finishStep` has TWO arms**: the failure backstop, whose predicate stays the inline `queued\|running`; and an expiry arm for a row still `awaiting_input` when the WORKFLOW IS ENDING — nothing can wake it now, so it expires the asks and settles `cancelled` with `error` NULL and `reason: 'expired'` on the event row. The one exception is a park the loop ABANDONED (`MAX_INTERRUPT_ROUNDS`), which arrives with `outcome.status === 'failed'` — **the outcome decides that, never the row** |

Rules:

- **Claim is the row, not the queue.** A retried step re-claims and a settled row is never rewritten. **Three status lists, and they diverge on purpose**: `ACTIVE_RUN_STATUSES` (`queued|running|awaiting_input`) is "still owes an answer" — the exclusive index, `findActiveRun`, `settle()`, `saveCheckpoint`; `CLAIMABLE_RUN_STATUSES` (`queued|running`) is `claimRun` ONLY; and `finishStep`'s backstop keeps its own inline `queued|running`, because widening THAT one turns every legitimately parked run into a `failed` row (its second, expiry arm is a separate branch, not a wider list).
- **Human-in-the-loop: `ctx.interrupt(ask)` parks the run**. `key` is the agent's and must be stable across attempts — a resumed `execute` re-enters `run()` from the top, and `UNIQUE (run_id, key)` is what makes the second call find the ANSWER. Everything after the call is **on the far side of a Worker deploy**, so side effects go behind `ctx.once`. **The answer is the transition**: resolving flips `awaiting_input → running` and only then nudges the instance, which is why `claimRun` needs no change. A rejection is `status: 'cancelled'`, never an `approved` boolean; what it MEANS is `rejectionFor(spec)` — `approval` stops the run (`InterruptDeclinedError` → `cancelled`, `error` NULL), everything else goes back to the model as an answer. `executeRun`'s catch arm writes **the rows first and parks second**: a row with no parked run re-asks, a parked run with no row hangs.
- **A gated tool is gated by the LOOP, never by its handler.** `Tool.requiresApproval` / `requiresApprovalWhen` make `runToolLoop` scan the whole turn after the assistant message is pushed and before any handler runs, checkpoint, and raise `InterruptRequested`. On resume, `resumePendingToolCalls` answers the trailing unanswered `tool_use` blocks through **the same** `executeToolUses` — do not fork it, or the gate is bypassed on the resume path only. Pass `approvals: ctx.approvals` and `runApproved: ctx.once` or an approved call re-executes on a step retry.
- **Exclusive = the partial unique index** `agent_runs_active_exclusive_idx` on `(tenant_id, agent_key, concurrency_key)`, active rows with a key only. `enqueueRun` picks the slot and writes it on the row: `input.concurrencyKey` when the caller narrows it (one active run per key, whatever `meta.exclusive` says), else `''` for an `exclusive` agent (one per tenant), else NULL — an agent with `exclusive: false` (one person's conversation with an agent) holds no slot, so every enqueue is its own run and never `deduplicated`. `findActiveRun` (the dedupe read) names the same slot (`''` by default). The migration backfilled `''` onto the active rows that existed before the column, so they keep the guarantee they were enqueued under. A non-exclusive agent is the one to batch — and the one whose runs are many, so its per-run budget is what bounds a bad day.
- **Fan out with `ctx.map`, never with `Promise.all` over `ctx` calls**. Two items calling `ctx.decide('relevant', …)` collide on `(run_id, key)` and the second gets the first's answer; `map` gives each item a scope. Freeze the item list (`once`) first, return jsonb from `fn`, and keep `keyOf` stable. A tool loop inside an item restarts on a retry (no per-scope checkpoint). Running another agent's body inline (`triage-research` → `research-topic`) stays a plain spread through `withFanout`, NOT a scope, because that body resumes from the run's checkpoint.
- **Usage is the meter's, never the agent's**: no `recordUsage` and no `onUsage` ledger write in an agent — `ctx.chat.client` and `ctx.decide` already write one row per call with the run id, and a second write double-counts. `ctx.recordUsage(call)` is for a client the agent built itself.
- **Cancellation is cooperative, then forced**: `requestCancel` sets the flag, the run's `checkCancelled()` polls between turns (and between tool results where the agent does the work in tools); `AgentCancelledError` is a TYPE the runtime maps to `cancelled`. A step in flight finishes. **The second cancel forces it** — terminate the instance, settle the row — because nothing polls in a hung model call or an orphaned instance, and an exclusive agent stuck `running` blocks the tenant. `reconcileRun` reads `terminated` as `cancelled`.
- **DB is the truth, WS is a nudge**: events go to `agent_run_events` first, then `entity.changed { entity: 'agent-run', id }`; viewers re-query `GET /api/agents/runs/:id`.
- **Per-agent model**: `resolveChat(..., { promptKey: meta.promptKey })` consults `agent_models`.
- **Every agent can read the knowledge base**: `ctx.tools` carries `search_knowledge` and `get_document` (everything indexed via `/documents` — pasted or uploaded — or an agent's `ingestText`). Pass `[...ctx.tools, ...ownTools, terminalTool]` to `runToolLoop`; a forced single-tool agent (`callStructuredTool`, like the example) simply does not use it. Never build a retrieval query from a model-supplied tenant id — the tool is bound to the run's tenant.
- **A retry re-enters `run()` from the top, so anything with a side effect goes through `ctx.once(key, fn)`** — an ingest, a ledger write, an outbound call. `agent_run_effects_run_key_idx` is the guarantee; the result is jsonb, so **return ids, not rows**. The contract is at-least-once WITH a recorded result, not exactly-once (an isolate that dies between `fn()` and the insert repeats the work).
- **A resumable loop passes `resume: await ctx.checkpoint.load()` and `onCheckpoint: ctx.checkpoint.save`**, so a retried step continues the conversation instead of replaying and re-billing it, and `maxTurns` becomes a budget for the RUN. State an agent derived from tool results DURING the loop (`research-topic`'s `seen` map) must be rebuilt from the resumed transcript — see `rehydrateSeen`; forget it and citations earned before the retry are silently dropped. A checkpoint that does not parse is `null`: the run starts fresh, never fails.
- **The tool loop runs INSIDE one `execute` step, deliberately.** One `step.do` per model turn was investigated once the durable transcript existed, and rejected: wall-clock per step is unlimited on Workflows (the 10-minute `timeout` is ours to raise), CPU per step excludes I/O and is configurable to 300 s, and per-turn retry is what the checkpoint already gives you. Per-turn steps would need `run()` to move outside `step.do` (steps do not nest), and Workflows replays everything outside a step — so every `emit`, cancel poll, `ctx.once` and tool call would need its own step or the timeline doubles. `docs/CONCEPTS.md` §9 Known gaps carries the full reasoning. Do not re-open it without a profile showing CPU, not I/O, is the limit.
- **A decision is a question, its consequence is code**. Ask with `ctx.decide` when the step
  is "what IS this?" — relevant, which category, how severe — and branch in TypeScript on the answer
  and its `confidence`. Keys follow `ctx.once`'s rule (stable, derived from a step name or an id).
  Anything a decision's ITEMS came from must be frozen first (`ctx.once`), or a replayed answer is
  mapped onto a different list. The `llm_self_report` fallback's numbers are not calibrated: never
  tune a production threshold on them without an eval.
- **An agent must stay replayable**: everything it learns from the outside world comes
  through `ctx` — `once`, `decide`, `interrupt`, `tools`, `chat` — because that is what the record
  holds. A query the agent runs itself on `ctx.db` replays against TODAY's data, not the run's.
  Mark a `once` whose `fn` is a pure model call `{ replay: 'rerun' }` so a live replay shows a
  prompt change; leave anything with a side effect on the default.
- Adding an agent: key in `@rocketflare/shared/ai/agents` (`CORE_AGENT_KEYS` + schemas) → prompt in `services/prompts.ts` → `examples/<key>.ts` → entry in `CORE_AGENTS`. No migration. (`AGENT_KEYS` / `AGENTS` are those plus every installed plugin's.)
